# filterline performance exploration — 2026-08-21

Review of `filterline.c` @ v0.1.7 (f630270) asking: can this run faster?

Short answer: yes, 3–6.5× wall clock, and the rewrite lands on the hard floor
for the problem. Prototype validated byte-identical to the current binary.

## Environment

- macOS 26.7 (Darwin 25.6.0), arm64 (Apple silicon)
- Apple clang 21.0.0, `cc -Wall -O3` (same as the Makefile)
- Benchmarks run with a warm page cache unless noted

## Benchmark data

```sh
# 20M lines, 48 bytes each, 960MB
awk 'BEGIN{for(i=1;i<=20000000;i++) printf "line %09d {\"id\":\"id-%07d\",\"name\":\"ABC\"}\n", i, i%5000000}' > big.F

# line numbers, sorted, no dups; ~10% selectivity (2,000,479 lines)
awk 'BEGIN{srand(42); for(i=1;i<=20000000;i++) if (rand()<0.1) print i}' > big.L

# plus sparse.L (0.1%) and dense.L (90%) for selectivity sweeps
```

## Root cause

`getline()` at `filterline.c:81` is the whole cost. It copies **every** line out
of the stdio buffer into `line` — including the ~90% of lines that are
immediately discarded. On top of that, `printf("%s", line)` at
`filterline.c:84` re-`strlen`s each kept line and takes the stdio lock per call.

The fix is to never copy: scan the read buffer with `memchr` and write kept
bytes **straight out of the input buffer**.

## Results

960 MB / 20M lines, warm cache, real / user seconds:

| workload                       | v0.1.7      | rewrite       | speedup     |
| ------------------------------ | ----------- | ------------- | ----------- |
| keep 10%                       | 0.61 / 0.55 | 0.18 / 0.12   | 3.4× / 4.6× |
| keep 0.1% (sparse, big skips)  | 0.57 / 0.46 | 0.19 / 0.13   | 3.0× / 3.5× |
| keep 90% (dense)               | 2.50 / 2.23 | 0.66 / 0.32   | 3.8× / 7.0× |
| `-v` (90% emitted)             | 1.29 / 1.18 | 0.20 / 0.14   | 6.5× / 8.4× |
| pipe in + pipe out (zstd case) | 0.70 / 0.61 | 0.21 / 0.14   | 3.3× / 4.4× |

`-v` gains most because the rewrite coalesces long runs of kept lines into
single large writes instead of 18M individual `printf` calls.

### This is the floor

A program that does nothing but `memchr` every newline in `big.F` costs
**0.12–0.13 s user**. The rewrite costs **0.12 s user**. It is now
`memchr`-bound; there is no meaningful CPU headroom left after this.

For reference, a bulk auto-vectorized newline count (`for(i) n += b[i]=='\n'`)
measured 0.12 s user vs 0.13 s for repeated `memchr` — i.e. repeated `memchr`
is already effectively free, so no hybrid bulk-count path is worth adding.

## Design of the rewrite

Single function that skips *or* emits N lines, over a raw `read()` buffer, with
its own output buffer and `write()` (bypasses stdio entirely):

```c
const unsigned char *p = base, *e = base + avail;
uint64_t found = 0;
while (found < need) {
  const unsigned char *nl = memchr(p, '\n', (size_t)(e - p));
  if (!nl) break;
  p = nl + 1; found++;
}
if (found == need) { take = p - base; done = n; r->partial = 0; }
else { take = avail; done += found; r->partial = (base[avail-1] != '\n'); }
if (emit) oput(base, take);   // writes from the input buffer; no copy
```

Keep mode: `skip(target-current-1)` then `emit(1)`.
Invert mode: `emit(target-current-1)` then `skip(1)`, then `emit_rest()`.

### Two bugs hit while building it (both worth remembering)

1. **`cnt <= need` vs `cnt == need` at the chunk boundary.** The first cut
   lumped the trailing partial line into the run whenever the count matched
   exactly, corrupting **one line per 1 MB refill** — e.g. emitting
   `line 000043691 {"id":"id-0043691line 000043693 {...}`. Invisible on
   `fixtures/`; only the 960 MB file exposed it. Any future change here needs a
   large-file diff, not just the fixtures.

2. **Counting newlines over the whole chunk before deciding.** The original
   structure ran `count_nl()` across the full 1 MB buffer on every call. With
   `-v` and ~9-line runs that is quadratic-ish: it ran 59 s and looked like a
   hang. Replaced with the single bounded `memchr` walk above, which never scans
   past what the run actually needs.

## What did NOT help

- **Bigger `stdout` buffer alone** (`setvbuf`): 0.59 vs 0.58 user. Nothing.
  The existing `setvbuf` calls at `filterline.c:74-76` aren't buying much either.
- **`printf` → `fputs`**: 26% on `-v`, ~5% on keep. Real and one line, but small
  next to 6.5×.
- **Buffer size above 64 KB**: flat when warm (64K/256K/1M/4M/16M all 0.12 user).
  4 MB does help *cold* (0.73 → 0.49 real) via readahead — worth raising
  `BUFFER_SIZE`, but that's an I/O win, not a CPU one.
- **`-march=native -flto`** (the commented-out Makefile line): hot work is libc
  `memchr`, already runtime-dispatched to SIMD. Leave it commented.

## Correctness issues found while reading

1. **A duplicate or out-of-order entry in L silently truncates the rest of the
   output.** `L=2,2,4` over `a,b,c,d` prints only `b` — line 4 is gone. README
   documents L must be sorted and dup-free, but silent data loss is the wrong
   failure mode for a compaction pipeline. Guard is one line:
   `if (target <= current) continue;`
2. **Write errors are ignored** (`filterline.c:97` and every `printf`). If the
   output disk fills mid-run, filterline exits **0** with a truncated snapshot.
   Given the Crossref use case, this is the one to fix regardless of perf.
3. **`unsigned int` counters** (`filterline.c:36-37`) cap at ~4.29e9 lines;
   README already cites 1e9-line inputs. `uint64_t` is free here.
4. `filterline.c:83` reads `line` after `getline` may have returned -1 —
   contents are not defined after a failed call. No bad emit observed on macOS,
   but not guaranteed.
5. Usage text goes to **stdout** and exits **0** (`filterline.c:49-56`); a failed
   `fopen` exits 1 with no message (`filterline.c:66-70`). Both should be
   stderr / non-zero.
6. `argc == 4` with `argv[1] != "-v"` silently ignores `argv[3]`.

## Validation performed

Prototype output compared byte-for-byte (`cmp`) against the v0.1.7 binary:

- `fixtures/` keep and `-v`
- 960 MB keep and `-v` at 0.1%, 10%, 90% selectivity
- no trailing newline on last line; empty F; empty L; L entries past EOF;
  a single 3 MB line (longer than the buffer); space-separated L
  (`<(echo 1 2 5 6)` form)
- F as a pipe (process substitution) and output to a pipe

All identical. The only intentional divergences are duplicate-L and unsorted-L,
where the prototype tolerates the input and the current version truncates.

ASan + UBSan clean across every case above, including the 960 MB runs.

## Open decision

Land the full rewrite as `filterline.c` (with robustness fixes 1–3 folded in),
or keep the change minimal and apply only fixes 1–3 to the existing structure.

The prototype lives in `hacking/filterline-fast/` (`make` to build,
`make check` for a differential test against the released binary on
`fixtures/`, `make sanitize` for an ASan+UBSan build). It does **not** yet
carry robustness fixes 1–3 beyond the `target <= current` guard it already has;
none of the correctness issues above are fixed in the released `filterline.c`.
